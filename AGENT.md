# Hướng dẫn cho agent

Đọc file này và các hướng dẫn toàn cục do môi trường cung cấp trước khi làm việc. Khi sửa code, đọc thêm tài liệu gần với phần thay đổi; nếu có quy tắc dự án áp dụng trực tiếp thì tuân theo.

## Dự án

Lumina CMS là CMS quản trị dùng Laravel 13, React 19, Inertia 3 và TypeScript. Backend nằm trong `app/`, route trong `routes/`, cấu hình trong `config/`; giao diện Inertia nằm trong `resources/js/`. Hệ thống generic resource dùng `App\Concerns\QueryBuilder`, `App\Support\ResourceResolver` và `App\Support\RuleSchemaConverter`. Settings và menu quản trị được chia sẻ qua `CmsServiceProvider`.

### Module cá nhân (Công việc)

Module `/tasks` và `/calendar` theo [`docs/design/DESIGN.md`](docs/design/DESIGN.md), nằm trong nhóm sidebar "Công việc" (`config/views.php`). Chi tiêu, Thói quen, Ghi chú đã bị bỏ ngày 2026-10-27 (quyết định D15); các bảng `expenses`, `habits`, `habit_logs`, `notes` nếu đã tồn tại trong DB không bị code này xoá.

- Công việc: model dùng `QueryBuilder`, CRUD qua `ItemController` và trang `resources/js/pages/tasks/{index,form}.tsx` dựng bằng `IndexLayout`/`FormLayout`. Thêm nhanh công việc: `components/tasks/quick-add-task.tsx`.
- Lịch (`/calendar`, nhóm "Công việc"): bảng `events`, model `Event` (`QueryBuilder`, `PERMISSION_RESOURCE = 'events'`, giờ là `time` `H:i` theo `cms.personal_timezone`, lặp `none|daily|weekly|monthly`, mốc nhắc `remind_before_minutes` = 1440/30 phút). `CalendarController` dựng trang tháng (`pages/calendar/index.tsx`, chỉ chế độ Tháng, chip lọc theo loại phía client, panel "Sắp tới" 5 sự kiện) và `GET /calendar/conflicts` (cảnh báo trùng giờ cùng ngày, không chặn). CRUD sự kiện qua items API và `pages/events/form.tsx` (`/events/create`, `/events/{id}`; `/events` chuyển về `/calendar`). `App\Support\EventSchedule` khai triển sự kiện lặp và tính nhắc đến hạn (thuần, không chạm DB).
- Nhắc lịch: `php artisan events:send-reminders` chạy mỗi phút trong `routes/console.php` (cần `schedule:run`/`schedule:work`), gửi `EventReminderNotification` (kênh database) cho admin tạo sự kiện, ghi `reminders_sent` để không gửi trùng; mốc đã qua nhưng sự kiện chưa bắt đầu vẫn nhắc (chỉ mốc gần nhất), sự kiện đã bắt đầu thì bỏ qua. Chưa có UI hiển thị thông báo trong app. Field form mới `choice-cards`, `checkbox-group` ở `components/form/field/`.
- Dashboard (route `/dashboard`, tên `dashboard`; `/` giờ là trò chuyện AI): `DashboardController` thêm thẻ tóm tắt `tasksSummary` (Inertia deferred) hiển thị bởi `components/dashboard/personal-summary.tsx`; phần CMS/Analytics giữ nguyên.
- Phân quyền: model khai báo `PERMISSION_RESOURCE` thì `App\Http\Middleware\AuthorizeResource` yêu cầu `{resource}.{view|create|update|delete}` (system admin có đủ) trên `items/*`, `api/items/*` và trang; model khác không bị ảnh hưởng. Quyền mới (gồm `events.*`) do `php artisan permissions:generate` tạo; bảng mới cần `php artisan migrate`. Model khai báo `SEARCH_FIELDS` thì `ItemController` tìm trong các cột đó.
- Ngày "hôm nay" của module tính theo `config('cms.personal_timezone')` (`Asia/Ho_Chi_Minh`), không đổi `app.timezone`; phía frontend hằng tương ứng ở `resources/js/lib/personal-date.ts`.

### Bài viết đa nền tảng (nhóm "Công việc", `/posts`)

Đăng và hẹn giờ đăng bài lên LinkedIn, Facebook Fanpage, Instagram (và hai kênh cá nhân không chính thức, xem dưới) (app web tự host, hẹn giờ bằng scheduler, không còn "bù khi mở lại app"). UI theo `docs/design/mockups/linkedin-posts*.png`, `linkedin-form*.png`.

- Bảng `posts` (`title`, `body`, `media` JSON `[{url,type}]`, `scheduled_at` UTC nhưng form nhập/hiện theo `cms.personal_timezone`, `status` draft|scheduled|publishing|published|partial|failed|missed) và `post_targets` (unique `post_id + provider + social_group_id` (nullable: không có nhóm = đăng lên trang cá nhân/Page như cũ; mục tiêu không nhóm vẫn duy nhất theo `provider` nhờ `PostController`), `status` pending|publishing|published|failed|unknown, `external_post_id`, `external_url`, `error`, `attempts`). Model `Post` dùng `QueryBuilder`, `PERMISSION_RESOURCE = 'posts'`; chỉ bài `draft`/`scheduled` sửa được. Quyền `posts.{view,create,update,delete,publish}` (`publish` cho hẹn giờ/đăng ngay/thử lại/hẹn lại).
- `PostController` + `SavePostRequest` (route `posts/*` đặt trước catch-all; trang `pages/posts/{index,form}.tsx`, `components/posts/*`). Chỉ nền tảng có Integration `connected` và đã bật quyền đăng mới chọn được; backend validate cả giới hạn ký tự theo nền tảng, kiểu media và Instagram bắt buộc có ảnh. Giới hạn/phiên bản API ở `config/posting.php`.
- Đăng bài: interface `PostPublisher` + `LinkedInPublisher`, `FacebookPublisher`, `InstagramPublisher` (Http facade). Mỗi publisher đọc thông tin kết nối từ Integration (LinkedIn: secret `access_token` + trường `author_urn`; Facebook: secret `page_access_token` + trường `page_id`; Instagram: secret `access_token` + trường `ig_user_id`). Thiếu trường thì target `failed` với "Chưa đủ thông tin kết nối để đăng", không giả thành công. Các trường này đã có trong form Tích hợp (`config/integrations.php`); đăng nhập bằng OAuth (xem dưới) hoặc dán token tay làm dự phòng.
- Không tự retry: timeout/`ConnectionException`/5xx ở request tạo bài thành `unknown` (nút "Đăng lại" có xác nhận "Có thể đã đăng"); lỗi 4xx thành `failed` ("Thử lại"). Chiếm việc bằng UPDATE nguyên tử (`pending→publishing`) ở `PostPublishingService` nên không đăng đôi. Trạng thái bài tổng hợp từ các target (published/partial/failed).
- Danh sách `/posts`: tab nhóm trạng thái (`status`: draft|scheduled|published|failed), lọc trạng thái chính xác `state` (7 trạng thái, thắng `status` khi gửi cùng lúc), lọc nền tảng `provider`, tìm `q` theo tiêu đề/nội dung (escape LIKE bằng ký tự `!` khai báo trong SQL nên `%`/`_` là ký tự thường ở mọi DB). Xoá cần `posts.delete`, có xác nhận, chặn bài `publishing`, không gỡ bài đã đăng trên nền tảng. Nhân bản (`POST posts/{post}/duplicate`, quyền `posts.create`): tạo bản nháp mới (title thêm " (bản sao)", bỏ `scheduled_at`, copy media và nền tảng ở trạng thái `pending`), không gửi gì và không đổi bài gốc.
- Đăng hàng loạt vào nhóm đã lưu (`social_groups`, chỉ `facebook_personal`/`linkedin_personal`): form bài chọn nhóm theo nền tảng (`groups` = `{provider: [id]}`, mỗi nhóm một `post_targets` có `social_group_id`). `PostsToGroups` (trait của hai publisher) gửi script `post` thêm `group_url` (chỉ nhận `https://www.facebook.com/groups/...` / `https://www.linkedin.com/groups/...`; khối `runGroupPost` thêm riêng trong `scripts/{facebook,linkedin}-post.mjs`, selector nhóm CHƯA kiểm với trang thật, nằm trong khối `FACEBOOK`/`LINKEDIN`). An toàn: dùng chung `posts_per_hour` và khoá RateLimiter của nền tảng (form chặn chọn quá giới hạn), `PostPublishingService` đăng tuần tự, nghỉ ngẫu nhiên `posting.group_posting.delay_{min,max}_seconds` giữa hai nhóm cùng nền tảng, gặp `checkpoint`/`not_logged_in`/chạm giới hạn giờ thì các nhóm còn lại của nền tảng đó thành `failed` (không đụng trang, bấm "Thử lại" sau), kết quả không chắc chắn vẫn là `unknown`, không tự đăng lại.
- `facebook_personal` (không chính thức, văn bản + ảnh (không video), chạy trên MÁY NÀY, cần máy bật, Google Chrome và Node): `scripts/facebook-post.mjs` (`playwright-core`, Chrome thật, hồ sơ riêng `storage/app/facebook-profile`; không stealth/giả vân tay/đổi header, gặp checkpoint thì dừng báo `checkpoint` để người dùng tự xử lý). Chế độ: `login` (`pnpm facebook:login`, tự đăng nhập tay một lần), `check` (`pnpm facebook:check`), `session` (kiểm tra đăng nhập, báo `loggedIn`, làm mới phiên đã lưu) và `post` (stdin JSON `{text, audience, images?: [url]}`; in một dòng JSON `{ok, via?: browser-api|ui, post_id?, url?, error?}` với mã lỗi cố định; ảnh http(s) được tải về thư mục tạm (≤10MB/ảnh, phải là `image/*`, tối đa `Post::MAX_MEDIA`), đính qua nút Ảnh/video, bấm `Tiếp` nếu có rồi `Đăng`; luồng ảnh/`Tiếp` CHƯA kiểm với Facebook thật). Bài chỉ văn bản đi qua 3 tầng, không bao giờ rơi xuống tầng dưới sau một kết quả mơ hồ: (1) `FacebookPersonalPublisher` gọi thẳng `Http` POST `https://www.facebook.com/api/graphql/` (`via: http`) với phiên và mẫu request script đã lưu (`FacebookWebSession`: nạp file, render mẫu giống script, phân loại phản hồi); chỉ gửi header `Cookie` và body form (không tự đặt User-Agent hay header nào khác; Guzzle vẫn gửi mặc định riêng của nó), không cần mở Chrome; (2) chỉ khi tầng 1 bị từ chối dứt khoát (HTTP 4xx, hoặc chỉ `errors` không có `data`, hoặc chưa có phiên/mẫu hợp lệ, hoặc bài có ảnh) mới chạy script `post` đúng một lần qua `FacebookBrowserScript` (`Process`, argv mảng, timeout 180 giây, `posting.facebook_personal.node_binary` / env `FACEBOOK_PERSONAL_NODE_BINARY`, `FACEBOOK_PERSONAL_HEADLESS`): request trong trang Chrome (`via: browser-api`) rồi giao diện (`via: ui`), đồng thời làm mới phiên/mẫu; (3) kết quả mơ hồ (5xx, timeout/lỗi kết nối, `data` không có mã bài, phản hồi không đọc được) là `unknown` và KHÔNG chạy tầng sau (tránh đăng đôi), vẫn tính vào giới hạn giờ. Log cố định `Facebook personal post published.` kèm `via` (`http`|`browser-api`|`ui`).
  - Trong script (tầng 2), bài chỉ văn bản có mẫu hợp lệ: đọc lại `fb_dtsg`/`lsd`/`jazoest` từ trang rồi `fetch('/api/graphql/')` NGAY TRONG trang, thay văn bản/đối tượng (`self→SELF`, `friends→FRIENDS`, `public→EVERYONE`, lạ→`SELF`) và sinh UUID mới cho id dạng UUID. Có mã bài → `{ok, via:"browser-api"}`; chỉ bị từ chối dứt khoát (4xx, hoặc chỉ `errors`) mới xoá mẫu và chạy giao diện đúng một lần; kết quả mơ hồ là `unknown`, không fallback. Bài có ảnh và bài đầu tiên (chưa có mẫu) đi qua giao diện.
  - File phiên `storage/app/facebook-session.json` (0600, gitignored, không bao giờ in/log; `posting.facebook_personal.session_file`): `user_id`, `fb_dtsg`, `lsd`, `jazoest`, `cookie_header` (do script ghi mỗi lần `session`/`post`) và `template`. Facebook đổi tham số/`doc_id` hoặc token hết hạn thì tầng 1 bị từ chối, script làm mới. Tầng 1 và mẫu CHƯA từng chạy với Facebook thật.
  - Script không xác nhận được bài lên (timeout, không thấy thông báo) là `unknown`; `not_logged_in` là `failed` ("chạy pnpm facebook:login"). "Kiểm tra kết nối" chạy `session` (làm mới phiên) rồi kiểm tra cục bộ file phiên đủ cho tầng HTTP chưa (không gọi Facebook), báo đã đăng nhập hay chưa. Tối đa `FACEBOOK_PERSONAL_POSTS_PER_HOUR` bài/giờ (chỉ tính bài `published`/`unknown`), không tự retry. Lần đầu: `pnpm install`, `pnpm facebook:login`.
- `linkedin_personal` (KHÔNG chính thức, văn bản + ảnh (không video), chạy trên MÁY NÀY, cần Chrome và Node): `scripts/linkedin-post.mjs` dựng cùng kiểu `facebook_personal` (`playwright-core`, Chrome thật, hồ sơ riêng `storage/app/linkedin-profile`, không stealth/giả vân tay/UA/header, không giải captcha/checkpoint: gặp thì báo `checkpoint`). ! Chế độ `login` (`pnpm linkedin:login`, cửa sổ luôn hiện, chỉ đóng khi cookie `li_at` đã có, chỉ kiểm sự hiện diện), `check` (`pnpm linkedin:check`), `session` (báo `loggedIn` và `template`), `post` (stdin JSON `{text, audience: public|connections, images?: [url]}`, tối đa 9 ảnh http(s) ≤10MB tải về thư mục tạm và xoá trong `finally`; in một dòng JSON `{ok, via?: browser-api|ui, post_id?, url?, error?}`, mã lỗi cố định như Facebook). Mẫu request lưu ở `storage/app/linkedin-session.json` (0600, gitignored, không cookie/token, không in/log), bắt lần đầu khi đăng văn bản qua giao diện. Lần đầu: `pnpm install`, `pnpm linkedin:login`.
- Đối tượng xem bài theo từng nền tảng: `config('posting.providers.<key>.audiences')` là map `giá trị => nhãn`, giá trị đầu là mặc định (`facebook_personal`: self/friends/public; `linkedin_personal`: public/connections). `SavePostRequest` kiểm theo nền tảng, `PostProviders` trả `audiences: [{value,label}]` cho form.
- Hẹn giờ: `php artisan posts:publish-due` chạy mỗi phút trong `routes/console.php` (cần `schedule:run`/`schedule:work`): đăng bài `scheduled` đến hạn, bài trễ quá `posting.late_after_minutes` (60) chuyển `missed` (UI "Đã lỡ lịch": Đăng ngay / Hẹn lại / Bỏ, quyết định D8), target `publishing` treo quá `stale_publishing_minutes` thành `unknown`. "Đăng ngay" chạy bằng `PublishPostJob::dispatchAfterResponse()`.

### Hộp thư chung (nhóm "Giao tiếp", `/inbox`)

Mục duy nhất của nhóm "Giao tiếp" trên sidebar (không còn mục "Tài khoản email"; `/mail/accounts` vẫn truy cập trực tiếp): danh sách bên trái gộp hội thoại chat và thư INBOX theo thời gian, thread bên phải. `/chat` và `/mail` vẫn hoạt động nguyên như cũ.

- `InboxController` (`GET /inbox`, `pages/inbox/index.tsx`): tham số `channel` (`all|email|<provider chat đã đăng ký>|zalo_group`, danh sách tab lấy từ `ChatChannels::providers()` cộng `email` và tách Zalo nhóm; nhãn Messenger là "Facebook"), `filter` (`all|unread`), `q`, `page`, và `c` (hội thoại) hoặc `m` (thư) để mở thread. Mỗi mục có `kind` (`chat|mail`), `key`, `channel`; thư dạng hội thoại (tên = người gửi, tin cuối = tiêu đề, chưa đọc = 1).
- Phân quyền theo từng kênh, kiểm trong controller: `conversations.view` cho chat, `mail.view` cho thư; thiếu một quyền thì kênh đó biến mất khỏi tab/danh sách/thread, thiếu cả hai thì 403. Trả lời không đổi: chat qua `POST chat/{conversation}/messages` (`conversations.reply`), thư qua `POST mail/messages/{id}/reply` (`mail.send`); đăng ký thêm `from_inbox` thì `MailController` redirect về `/inbox?m=` thay vì `/mail/messages/{id}`.
- Truy vấn: hai select có chỉ mục (`conversations`, `mail_messages` thuộc INBOX) `UNION ALL` rồi sắp xếp (`sort_at` rỗng cuối, rồi `id`) và `paginate` 30 mục/trang bằng SQL, sau đó nạp chi tiết bằng một query mỗi bảng (kèm quan hệ kênh/mailbox) nên số query không tăng theo số dòng (test đếm query). Sắp xếp trên kết quả gộp phải quét id của cả hai bảng; chấp nhận được ở quy mô cá nhân. Tìm kiếm dùng `LIKE ... escape '!'` cho cả hai nguồn.
- Dùng chung với `/chat` và `/mail`: `ChatThreadPresenter` (mở thread chat: đánh dấu đã đọc, phân trang tin, dựng dữ liệu), `MailThreadPresenter` (mở thư: tải thân, đặt đã xem, luồng thư, lịch sử gửi), `components/chat/chat-thread-pane.tsx`, `components/mail/mail-thread-content.tsx`, `ConversationList`, hook `use-live-reload` (realtime/poll). Props `mailThread` chỉ chạy khi truy cập mục đó, reload live không mở lại thư (không gọi IMAP mỗi vài giây). Badge sidebar `inbox_unread` = chưa đọc chat + chưa đọc INBOX.

### Chat đa kênh (nhóm "Giao tiếp", Telegram, Zalo và Messenger)

Trang `/chat` (`ChatController`, `resources/js/pages/chat/index.tsx`, `components/chat/*`) theo hành vi của [`docs/design/multi-channel-chat-ui.md`](docs/design/multi-channel-chat-ui.md). Có ba kênh: Telegram, Zalo cá nhân (QR) và Messenger cá nhân (cookie, qua mautrix-meta — xem mục riêng bên dưới); chưa có Discord/WhatsApp hay nhãn (trợ lý AI: xem mục "Trợ lý AI").

- Bảng `conversations` (unique `provider + external_chat_id`, `unread_count`, preview tin cuối) và `chat_messages` (unique `conversation_id + external_message_id` để chống trùng tin nhận; `client_token` unique để chống gửi đúp). Model `Conversation` dùng `QueryBuilder`, `PERMISSION_RESOURCE = 'conversations'`; quyền `conversations.view` (xem) và `conversations.reply` (trả lời) do `permissions:generate` tạo.
- Thông tin bot lấy từ `Integration` `telegram` (token mã hoá). `TelegramChannel` là nơi duy nhất đọc token; chỉ chạy khi `status = connected` và quyền "Nhận/Gửi tin nhắn" của kết nối còn bật. Token lỗi 401 đặt `status = error` + `last_error`, UI hiện banner "Mất kết nối" và khoá ô nhập. Không bao giờ log token hay message của `ConnectionException` (chứa URL có token).
- Nhận tin: `php artisan chat:telegram-poll` (long-poll `getUpdates`, offset lưu ở `integrations.meta.telegram_offset`, chỉ ack sau khi lưu xong, tin lặp bị bỏ nhờ unique). Tin không phải text lưu dạng "Loại tin chưa hỗ trợ: <loại>". Chạy nền bằng supervisor (`php artisan chat:telegram-poll`, tự chờ khi chưa kết nối) hoặc scheduler gọi `chat:telegram-poll --once` mỗi phút (chưa khai báo trong `routes/console.php`; thêm khi triển khai). Chỉ một poller cho mỗi bot và bot không được đặt webhook (Telegram trả 409).
- Gửi tin: chỉ trả lời hội thoại đã có, không có tự động gửi/bot. `TelegramSender` thử đúng một lần, không retry: timeout/`ConnectionException`/5xx thành `unknown` ("Chưa chắc chắn", nút "Gửi lại" có xác nhận "Có thể gửi trùng"), lỗi HTTP rõ ràng thành `failed` ("Thử lại"). `resend` chiếm tin bằng một UPDATE nguyên tử nên bấm đúp không gửi hai lần; `sending` treo quá 2 phút được coi là `unknown` khi mở hội thoại.
- Mở hội thoại (`GET /chat?c=`) đặt `unread_count = 0`. Trang cập nhật realtime qua Pusher Channels (xem mục "Realtime /chat"); chưa cấu hình Pusher thì partial reload mỗi 5 giây (tạm dừng khi tab ẩn). Tin nhắn phân trang theo cursor `before` (50 tin/lần, `GET /chat/{conversation}/messages`). Badge chưa đọc ở sidebar (mục Hộp thư chung, `badge_source = inbox_unread`) do `CmsServiceProvider` điền trong `config/views.php`; sidebar không còn mục Chat riêng nhưng `/chat` vẫn truy cập trực tiếp.

#### Kênh Zalo (đăng nhập QR, không chính thức)

- Sidecar `zalo-bridge/` (Node >= 20, thư viện `zca-js` ghim 2.2.0) giữ kết nối Zalo; Laravel chỉ nói chuyện với sidecar qua HTTP loopback có chữ ký HMAC dùng chung `ZALO_BRIDGE_SECRET` (hai chiều). Sidecar luôn bind 127.0.0.1, không ghi credentials, ảnh QR hay nội dung tin ra log/đĩa.
- Đăng nhập: trang riêng `/integrations/zalo` (`pages/integrations/zalo.tsx`, chọn bằng khoá `page` trong `config/integrations.php`; không có nút Lưu/Kiểm tra/Huỷ, không "Quyền và phạm vi" hay card "Trạng thái" cấp kênh). Danh sách tài khoản dùng `components/tables/data-table.tsx` qua `components/integrations/integration-accounts-table.tsx` (dùng chung với Messenger): cột Tài khoản, Trạng thái, Kiểm tra lần cuối, Kết nối lúc, Hành động (Cài đặt / Đồng bộ danh bạ / Ngắt kết nối có xác nhận). "Thêm tài khoản" mở popup `zalo-account-dialog.tsx`: cảnh báo kết nối không chính thức, "Tôi hiểu rủi ro", quyền và chế độ nhóm của tài khoản đó, rồi `zalo-qr-panel.tsx` (mã QR) quét bằng Zalo trên điện thoại và xác nhận; "Cài đặt" mở lại popup ở chế độ sửa quyền/chế độ nhóm. Phiên của từng tài khoản do Laravel lưu mã hoá trong `zalo_accounts.credentials`; sidecar chỉ giữ trong bộ nhớ và xin lại qua `GET /internal/zalo/accounts` + `GET /internal/zalo/session?account=` khi khởi động lại, nên khởi động lại sidecar không cần quét lại.
- Đa tài khoản: bảng `zalo_accounts` (`account_key` = uid Zalo duy nhất, `credentials` mã hoá, `status`, `permissions` JSON null = mặc định, `group_mode`, `bridge_state(_at)`, `connected_at`, `contacts_synced_at`) và `conversations.zalo_account_id` (FK nullOnDelete) + `conversations.account_scope` (id tài khoản, 0 với Telegram/Messenger) nằm trong khoá duy nhất `(provider, external_chat_id, account_scope)`, nên cùng một người bạn nhắn hai tài khoản cho hai hội thoại riêng. `ZaloChannel` (tài khoản, credential, trạng thái theo tài khoản, `refreshStatus` suy trạng thái kênh), `ZaloInbox` (gán hội thoại vào tài khoản, quyền `receive` và `group_mode` theo tài khoản), `ZaloSender` (gửi đúng tài khoản của hội thoại, quyền `reply`/`proactive` và rate limit `zalo-send:{id}` theo tài khoản), `ZaloContactSync` (đồng bộ danh bạ theo tài khoản). Zalo đăng ký vào `ChatChannels` như Messenger qua driver `ZaloChatChannel` (cùng khoá `conversation.account`, chip tên tài khoản ở `/chat` khi có hơn 1 tài khoản). Route: `PUT/DELETE integrations/zalo/accounts/{account}` và `POST integrations/zalo/accounts/{account}/contacts/sync` (đều `integrations.update`); QR `POST/GET/DELETE integrations/zalo/qr` không còn đăng xuất tài khoản đang chạy, nhận `permissions[]` + `group_mode` và áp dụng cho tài khoản vừa đăng nhập khi trình duyệt hỏi trạng thái `logged_in` (lưu tạm trong cache theo `login_id` 10 phút; trước lúc đó tài khoản mới dùng quyền mặc định). Sidecar giữ mỗi tài khoản một `ZaloSession` trong `SessionManager` (xem `zalo-bridge/README.md`); không gửi `account` (client cũ) chỉ hợp lệ khi có đúng một tài khoản. Migration `2026_10_31_000005_create_zalo_accounts_table` đổi phiên Zalo cũ trên integration thành tài khoản đầu tiên (idempotent, giữ nguyên credentials cũ ở `integrations`) và gắn mọi hội thoại Zalo cũ vào đó.
- Callback `routes/internal.php` (đặt dưới `internal/zalo`, chỉ middleware chữ ký + throttle, không session/CSRF): `session` (POST/GET, GET nhận `?account=`), `accounts`, `status`, `inbound` (status/inbound mang `account`). Tin nhận qua `ZaloInbox`, gửi qua `ZaloSender` (có giới hạn tốc độ `ZALO_BRIDGE_SEND_GAP_MS`/`ZALO_BRIDGE_SEND_PER_MINUTE`). Chế độ nhóm `group_mode` theo từng tài khoản: `mention_only`, `all`, `off`.
- Chạy sidecar: `npm --prefix zalo-bridge install` (một lần), `npm --prefix zalo-bridge start` (nạp `.env` ở thư mục gốc), `npm --prefix zalo-bridge test`. Cần tiến trình chạy liên tục; supervisor/launchd chưa có trong repo.
- Biến môi trường (xem `.env.example`): `ZALO_BRIDGE_URL`, `ZALO_BRIDGE_PORT`, `ZALO_BRIDGE_SECRET`, `ZALO_BRIDGE_CALLBACK_URL`, `ZALO_BRIDGE_SEND_GAP_MS`, `ZALO_BRIDGE_SEND_PER_MINUTE`. Phải tự đặt `ZALO_BRIDGE_SECRET` là chuỗi ngẫu nhiên đủ dài trong `.env` (không commit); thiếu thì sidecar thoát mã 1.
- Cần ít nhất 2 worker PHP vì Laravel gọi sidecar trong khi sidecar gọi ngược callback: dùng `PHP_CLI_SERVER_WORKERS=4 php artisan serve` hoặc php-fpm. Nếu Laravel không chạy cổng 8000, đặt `ZALO_BRIDGE_CALLBACK_URL` đúng địa chỉ (viết literal, `node --env-file` không mở rộng `${APP_URL}`).
- Giới hạn/rủi ro: dùng API không chính thức, có thể vi phạm điều khoản Zalo và tài khoản có thể bị cảnh báo/khoá (nên dùng tài khoản phụ); chỉ một listener cho mỗi tài khoản nên mở Zalo Web ở nơi khác sẽ đá listener (displaced, có thể phải quét lại); hàng đợi tin nhận nằm trong bộ nhớ sidecar nên tắt sidecar khi còn tin chưa chuyển có thể mất tin.
- Danh bạ: sau khi đăng nhập, `/chat` có sẵn bạn bè và nhóm Zalo (chỉ tên, không kéo lịch sử tin). Sidecar `GET /contacts?account=` (ký HMAC) gọi zca-js `getAllFriends` (1 request), `getAllGroups` (chỉ lấy id) rồi `getGroupInfo` theo lô 50 nhóm nghỉ 1 giây để lấy tên, tối đa 5000 bạn và 500 nhóm, cache trong bộ nhớ 5 phút, không log tên/số điện thoại. `ZaloContactSync` (Laravel) upsert `Conversation` (provider `zalo`, `external_chat_id` = thread_id, tiêu đề = tên; tên rỗng không ghi đè tiêu đề; không tạo `ChatMessage`, không đụng Telegram). Chạy tự động một lần sau mỗi lần quét QR mới (sidecar báo `running` → `ZaloBridgeController::status` chạy `SyncZaloContactsJob` của tài khoản đó sau response, đánh dấu `zalo_accounts.contacts_synced_at`) và thủ công bằng nút "Đồng bộ danh bạ" ở dòng tài khoản (`POST /integrations/zalo/accounts/{account}/contacts/sync`, quyền `integrations.update`, throttle 3 lần/10 phút); trạng thái rỗng của `/chat` chỉ có nút dẫn tới trang Zalo. Hội thoại chưa có tin xếp sau hội thoại có tin (`last_message_at` null cuối danh sách); gửi chủ động vẫn bị chặn khi quyền `proactive` tắt và composer báo lý do.
- Testcase thủ công cần tài khoản thật: [`docs/repo/zalo-qr-channel-testcases.md`](docs/repo/zalo-qr-channel-testcases.md) (mọi dòng `Not Run`).

#### Kênh Messenger (cookie, không chính thức)

Laravel là Matrix client của một homeserver nội bộ (Synapse); mautrix-meta (bridgev2) giữ phiên Meta và tạo portal room. #### Realtime /chat (Pusher Channels)

- Laravel chỉ phát tín hiệu "có thay đổi" `ChatChanged` (`ShouldBroadcastNow`, đồng bộ vì queue là `database` và không có worker) lên private channel `chat` với payload `kinds` + `conversation_ids` (tối đa 50); không có nội dung tin, tên hay credentials. Trình duyệt nhận tín hiệu rồi `router.reload` các prop `LIVE_PROPS` nên mọi kiểm quyền của `/chat` vẫn áp dụng. `POST /broadcasting/auth` chỉ cho admin có `conversations.view` (system admin có đủ); Echo xác thực bằng axios `api` (không có meta csrf).
- `ChatRealtime` (singleton) gom thay đổi và phát một lần sau commit (rollback thì không phát). Event model đăng ký trong `AppServiceProvider` cho `ChatMessage`, `Conversation`, `Integration` (chỉ telegram/zalo, khi đổi `status`/`last_error`/`settings`); ghi bằng query builder (`insertOrIgnore`, bulk `update`) và chỉ đổi `meta` không phát. Mọi lỗi Pusher bị bắt, log đúng câu "Chat realtime broadcast failed." rồi nghỉ 60 giây (cache `chat-realtime:backoff`); timeout HTTP tới Pusher 2s/3s trong `config/broadcasting.php`. Không retry phát.
- Frontend (`lib/echo.ts`, `hooks/use-chat-realtime.ts`, `components/chat/realtime-status.tsx`): Echo chỉ khởi tạo khi build có `VITE_PUSHER_APP_KEY` và chỉ ở `/chat`. Đang kết nối thì không poll; mất kết nối poll 30 giây và reload một lần khi nối lại; tab ẩn không poll (hiện lại thì reload); đang gửi tin thì hoãn reload. Chưa cấu hình giữ poll 5 giây, chỉ báo ẩn.
- Bật: tự tạo app Pusher Channels, điền `PUSHER_APP_ID`, `PUSHER_APP_KEY`, `PUSHER_APP_SECRET`, `PUSHER_APP_CLUSTER` và `BROADCAST_CONNECTION=pusher` trong `.env` (không commit; `VITE_PUSHER_*` lấy từ các biến này), xoá cache cấu hình, rồi `pnpm run build` (biến `VITE_*` được nhúng lúc build). Tắt: `BROADCAST_CONNECTION=null`, bỏ `VITE_PUSHER_APP_KEY`, build lại để về poll 5 giây. Hạn mức gói Pusher: xem trang pricing của Pusher; hết hạn mức thì lỗi được bắt, server vẫn chạy và trang tự poll 30 giây.
- Giới hạn: mỗi commit có thay đổi chat gọi một request HTTP tới Pusher (Telegram batch N tin tối đa N tín hiệu); hội thoại mới từ `ZaloContactSync` (`insertOrIgnore`) hiện ở lần reload kế tiếp; chỉ `/chat` kết nối, badge sidebar ở trang khác không realtime. Phương án thay thế tự host: Laravel Reverb (cùng giao thức Pusher, `BROADCAST_CONNECTION=reverb` + `REVERB_*` + broadcaster `reverb` ở Echo, cần tiến trình `php artisan reverb:start` chạy liên tục); chưa cài.
- Testcase thủ công cần Pusher thật: [`docs/repo/chat-realtime-pusher-testcases.md`](docs/repo/chat-realtime-pusher-testcases.md) (mọi dòng `Not Run`).

Mật khẩu không bao giờ tới client (chỉ `has_password` và mask ở form sửa; để trống khi sửa thì giữ mật khẩu cũ). Cấu hình Email cũ (form `integrations`) không được chuyển; `/mail/accounts` báo và có nút xoá.
- Đồng bộ: `php artisan mail:sync {--mailbox=} {--force}` mỗi phút trong `routes/console.php` (cần `schedule:run`/`schedule:work`); mỗi hộp thư theo `sync_interval_minutes` (1/5/15/30). Lần đầu lấy `MAIL_CLIENT_INITIAL_DAYS` ngày, tối đa `MAIL_CLIENT_INITIAL_LIMIT` thư; sau đó chỉ UID mới (theo UIDVALIDITY), đối soát thư đã xoá và cờ đã đọc. Sai tài khoản/mật khẩu thì hộp thư `error` và bị bỏ qua cho tới khi lưu lại hoặc bấm "Thử lại". Không xoá/di chuyển thư trên máy chủ; chỉ đồng bộ INBOX và Sent (không đọc Spam).
- Đọc thư `/mail` (`MailController`, `pages/mail/{index,show}.tsx`, `components/mail/*`, quyền `mail.view`): tab Hộp thư đến/Đã gửi, lọc hộp thư, chưa đọc, tìm (LIKE trên tiêu đề, người gửi, địa chỉ, snippet; `%` `_` được escape), 50 thư/trang, tự làm mới 60 giây (`usePoll`). Mở thư tải thân qua `MailBodyLoader` (một phiên IMAP, peek) rồi đặt `\Seen`; lỗi máy chủ thì giữ trạng thái trong app (`flags_dirty`) và đẩy lại ở lần đồng bộ sau. HTML qua `HtmlBodySanitizer` rồi hiển thị trong `<iframe sandbox>` (không script, CSP chặn ảnh từ xa tới khi bấm "Hiện ảnh"); đính kèm chỉ liệt kê, không tải. Sidebar không còn mục "Email" riêng: đọc/trả lời thư nay có thể làm trong Hộp thư chung `/inbox`, badge chưa đọc gộp ở mục đó (`badge_source = mail_unread` vẫn còn trong `CmsServiceProvider`, INBOX của hộp thư chưa ngắt).
- Trả lời (quyền `mail.send`, throttle 20/phút; gửi lại 10/phút): `MailSender` gửi văn bản thuần qua SMTP riêng của hộp thư, From luôn là chính hộp thư, giữ luồng bằng In-Reply-To/References. Không retry: lỗi trước khi giao (kết nối/đăng nhập) là `failed` ("Thử lại"), lỗi/timeout sau khi bắt đầu giao là `unknown` ("Gửi lại" có xác nhận "Có thể gửi trùng"); `client_token` chống gửi đúp, gửi lại chiếm bằng UPDATE nguyên tử và giữ Message-ID; `sending` quá 2 phút hiện `unknown`. Sau khi gửi: đặt `\Answered` và (nếu `save_sent_copy`) APPEND vào Sent, đều best-effort (lỗi chỉ đặt `sent_copy_saved = false`).
- Log chỉ có câu cố định, `mailbox_id` và tên lớp ngoại lệ, không địa chỉ, tiêu đề, nội dung hay thông điệp thư viện.
- Giới hạn: Outlook/Microsoft 365 có thể bắt OAuth nên báo sai mật khẩu; DNS rebinding giữa lúc kiểm host và lúc kết nối chưa chặn hết; chưa kiểm với hộp thư thật. Testcase thủ công: [`docs/repo/email-mailbox-testcases.md`](docs/repo/email-mailbox-testcases.md) (mọi dòng `Not Run`). Biến môi trường: `MAIL_CLIENT_ALLOW_PRIVATE_HOSTS`, `MAIL_CLIENT_INITIAL_DAYS`, `MAIL_CLIENT_INITIAL_LIMIT` (xem `.env.example`, `config/mailbox.php`). Quyền `mail.{view,send}` do `permissions:generate` tạo.

### Tích hợp (14 kết nối)

Icon rail "Tích hợp" (icon `Plug`, giữa "Công việc" và "Thiết lập"; nhóm "Giao tiếp" nằm đầu rail) chỉ có 1 mục nên bấm đi thẳng tới trang tổng quan `GET /integrations` (`integrations.index`, `pages/integrations/index.tsx`): lưới thẻ chia nhóm (Trợ lý AI, Tin nhắn, Mạng xã hội & đăng bài, Lịch, Việc làm) với badge trạng thái và nút "Quản lý kênh"/"Thiết lập" tới `/integrations/{provider}`. Dữ liệu từ `IntegrationManager::overview()` (1 query trạng thái, không lộ credentials). Trang chi tiết có link "Tích hợp" quay về tổng quan.

- Định nghĩa provider (trường form, quyền/phạm vi, các bước kết nối, cờ `unofficial`) ở `config/integrations.php`; nhóm hiển thị (`categories` + khoá `category` của từng provider) và thứ tự thẻ cũng ở đó.
- `IntegrationController` + `UpdateIntegrationRequest` (allowlist theo định nghĩa) + trang `resources/js/pages/integrations/show.tsx`. Model `Integration`: `credentials` cast `encrypted:array`, hidden; client chỉ nhận mask 4 ký tự cuối. Kết nối không chính thức (Zalo, Messenger, WhatsApp, Instagram cá nhân) bắt buộc tick "Tôi hiểu rủi ro". `facebook` chỉ còn kết nối Fanpage chính thức; field dán cookie Messenger cá nhân (`messenger_token`/`messenger_account`, quyền `personal_messenger`) đã gỡ khỏi provider này, dùng provider `messenger` riêng.
- `test()` thật có cho Telegram (`getMe`), Zalo (`test = zalo`, qua sidecar) và Messenger (`test = matrix_bridge`, qua Provisioning API — xem mục Chat đa kênh); provider khác trả "Chưa hỗ trợ kiểm tra kết nối" và trang chi tiết ẩn nút "Kiểm tra kết nối" (`can_test`). Đăng nhập QR (`login = qr`) chỉ có cho Zalo (trang riêng, nhiều tài khoản; "Kiểm tra kết nối" generic không còn trên trang Zalo); đăng nhập cookie qua bridge (`login = matrix_bridge`) chỉ có cho Messenger. Chưa có adapter chat Lark/AI/WhatsApp/OAuth (ngoài LinkedIn).
- Khoá `active` trong `config/integrations.php` = provider có runtime thật: `true` cho telegram, zalo, linkedin, facebook, instagram (chat Telegram, chat Zalo qua QR, đăng bài bằng token); `true` thêm cho itviec (đọc việc làm công khai) và email (IMAP/SMTP, xem mục Email); `true` thêm cho ai (xem mục Trợ lý AI); `false` cho whatsapp, discord, lark, gcal, topcv (chỉ lưu cấu hình, chưa nhận/gửi/đồng bộ) và cho `messenger` (runtime đã có đủ nhưng chưa được người dùng tự test bằng bridge thật — xem mục Chat đa kênh; kênh vẫn luôn hiện trong `/chat`, khác các provider `active=false` còn lại). Chỉ provider `active=false` có Integration `connected` mới được trình bày là "Đã lưu cấu hình" (màu trung tính, thẻ tổng quan nút "Thiết lập") và trang chi tiết có ghi chú "Kênh này chưa hoạt động"; `status` trong DB không đổi (`IntegrationManager::statusLabel`). WhatsApp chưa có đăng nhập QR dù khoá `unofficial` vẫn bắt tick rủi ro. Integration `zalo` cũ đang `connected` từ thời chỉ lưu cấu hình (chưa có phiên QR) không có tài khoản nào: trang Zalo hiện bảng rỗng, chỉ cần "Thêm tài khoản" và quét QR.
- LinkedIn OAuth (cá nhân): `login = oauth` trong `config/integrations.php`, cấu hình `config/services.php` khối `linkedin` (env `LINKEDIN_CLIENT_ID`, `LINKEDIN_CLIENT_SECRET`, tuỳ chọn `LINKEDIN_REDIRECT_URI`, mặc định route callback; scope `openid profile w_member_social`). `POST /integrations/linkedin/oauth/start` (tạo `state` lưu session, chuyển hướng bằng `Inertia::location`) và `GET /integrations/linkedin/oauth/callback` (kiểm `state` bằng `hash_equals` rồi xoá, xử lý `error`, đổi code lấy token, gọi userinfo) trong `LinkedInOAuthController` + `Services/Integrations/LinkedInOAuth`, quyền `integrations.update`. Lưu `credentials.access_token` (mã hoá), `settings.fields.author_urn` = `urn:li:person:{sub}` (đúng nơi `LinkedInPublisher` đọc), `meta.{expires_at, account_name, connected_via}`; không log/flash/props code hay token, không log message ngoại lệ HTTP. Không tự refresh token; trang hiện "Hết hạn" khi `meta.expires_at` đã qua và cảnh báo khi còn dưới 7 ngày. Form dán token thủ công được thu gọn làm dự phòng (lưu token mới sẽ xoá `expires_at` cũ). Endpoint/scope chưa đối chiếu tài liệu LinkedIn hiện hành. Testcase thủ công: `docs/repo/linkedin-oauth-testcases.md`.
- Provider có khoá `manage_url` (email = `/mail/accounts`) không có form chung: `GET /integrations/email` chuyển hướng tới đó và trạng thái thẻ tổng quan lấy từ bảng `mailboxes` (có lỗi > có kết nối > chưa kết nối).
- Phân quyền `integrations.{view,update}` (middleware `AuthorizeResource`); cần chạy `php artisan migrate` và `php artisan permissions:generate`.

## Lệnh phát triển

```bash
composer run dev          # chạy Laravel và Vite
composer run lint         # format PHP bằng Pint
composer run lint:check   # kiểm tra format PHP
composer run types:check  # PHPStan/Larastan
pnpm run format           # format frontend theo cấu hình dự án
pnpm run format:check     # kiểm tra format frontend
pnpm run check            # lint frontend bằng Vite Plus
pnpm run types:check      # kiểm tra TypeScript
pnpm run build             # build frontend
npm --prefix zalo-bridge install  # cài phụ thuộc sidecar Zalo
npm --prefix zalo-bridge start    # chạy sidecar Zalo (cần ZALO_BRIDGE_SECRET trong .env)
npm --prefix zalo-bridge test     # test sidecar (node --test)
```

`composer run setup` tạo lại `APP_KEY`. Với dự án đã có dữ liệu, dùng các bước cài đặt hoặc migrate cần thiết riêng, không chạy setup một cách máy móc.

## Quy ước triển khai

- Đọc implementation hiện tại và dùng component, pattern, thư viện đã có; giữ phạm vi thay đổi sát yêu cầu.
- TypeScript không dùng `any`; ưu tiên type có sẵn hoặc khai báo type theo domain.
- Không thêm dependency nếu chưa được yêu cầu. Không chạy migration trên database thật nếu chưa được yêu cầu rõ.
- Sau khi sửa, chạy formatter/linter hiện có trên đúng phạm vi file. Chỉ chạy test khi yêu cầu công việc có yêu cầu kiểm thử; không khẳng định đã chạy nếu chưa chạy.
- Giữ tương thích với Laravel Wayfinder: route/action sinh tự động trong `resources/js/routes/` và `resources/js/actions/`, không sửa tay các file sinh này.
- UI hiện có là chuẩn; chỉ thay đổi giao diện trong phạm vi người dùng yêu cầu.

## Luồng CRUD tổng quát

`ResourceResolver` phân giải tên resource sang model theo `config/core.php`. Model dùng `App\Concerns\QueryBuilder` có thể cung cấp truy vấn danh sách CRUD headless; `RuleSchemaConverter` tạo schema từ model và database để giao diện form dùng chung. Trước khi thay đổi luồng này, kiểm tra controller, trait và trang Inertia liên quan để giữ nguyên contract API.

Resource routes gọi `ItemController` hoặc `ViewController`. Trang theo feature nằm trong `resources/js/pages/`; UI tái sử dụng đặt trong `resources/js/components/`. Các file Wayfinder trong `resources/js/actions/` và `resources/js/routes/` được sinh từ backend; sửa route/controller nguồn rồi để công cụ sinh lại, không chỉnh tay file generated.
